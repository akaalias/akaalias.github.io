"Access To Tools"

Just yesterday Alex and I were discussing the need for better day-to-day vocabulary even as a user of language models.

Thankfully, the people of Olmo 3 were way ahead and are putting a stake in the ground that open AI development should include access to all layers of a models' creation.

To truly advance open AI development and research, the entire model flow – not just its endpoint – should be accessible and customizable.

The model flow is the full lifecycle of an LM: every stage, checkpoint, dataset, and dependency required to create and modify it. By exposing this complete process, the goal is to engender greater trust and enable more effective adaptation, collaboration, and innovation.

All participants are responsible for their own experience and learning. The Rules of Bar Camp

  • 1st Rule: You do talk about Bar Camp.
  • 2nd Rule: You do blog about Bar Camp.
  • 3rd Rule: If you want to present, you must write your topic and name in a presentation slot.
  • 4th Rule: Only three word intros.
  • 5th Rule: As many presentations at a time as facilities allow for.
  • 6th Rule: No pre-scheduled presentations, no tourists.
  • 7th Rule: Presentations will go on as long as they have to or until they run into another presentation slot.
  • 8th Rule: Presentations promoting specific comercial products or companies are discouraged.
  • 9th Rule: If this is your first time at BarCamp, you HAVE to present. (Ok, you don't really HAVE to, but try to find someone to present with, or at least ask questions and be an interactive participant.)

Hey all! I wanted to share a kind of new development process I’ve been using lately — I call it "Moonwalk."

Basically it's:

  • Check out a spike branch (git checkout -b reconciliation/spike/mt940)
  • Vibe code fast (and with vim and vigour!) until it feels just right
  • Generate a spec based on the final version
  • Switch back to main (git checkout main)
  • Check out only the spec (git checkout reconciliation/spike/mt940 -- /job-stories) <- This is the moonwalk!
  • Let the "professional" agents and sub-agents write production-grade code based on the spec

It's so effective because I can leverage Claude Code for both: Quickly build a working vibe-heavy prototype spec AND write production-grade code with agentic/sub-agentic quality.

For the vibe code part, the standard Claude Code top-level agent is more than sufficient. It's great, no need for time-costly delegation to sub-agents here.

For the production-grade part, since we're an XP shop with a pretty solid TDD process, sub agents make total sense. We turned our existing process and skills into a bunch of sub-agents that work smoothly together:

We've got...

  • green-minimal-implementer(.)md
  • code-quality-reviewer(.)md
  • code-refactorer(.)md
  • db-migration-specialist(.)md
  • dependency-manager(.)md
  • frontend-design-specialist(.)md
  • locale-translation-specialist(.)md
  • red-test-writer(.)md

So, yeah, that's what I wanted to share with you. Try it out and let me know how I can help :)

Cheers!

PS: For better or worse, this post is 100% written by hand
PPS: My friend Alex Fedorov reminded me that this is pretty close to the spike/exploration workflow we used to do at Pivotal Labs. I think he's right.
